# 加解密总览

> 作者：王有政
>
> 编码：UTF-8

本目录分成两个层级：

1. 基础算法：说明业务代码可以直接使用的密码学能力，以及每种密钥由谁生成、如何保存。
2. 场景与协议：说明接口、License、SSH、HTTPS/TLS 如何组合基础算法解决实际问题。

不能把 RSA、Ed25519、SSH、HTTPS/TLS 放在同一个列表中选择。它们不在同一层级：

```text
基础算法与能力
├── 对称加密：AES-GCM、ChaCha20-Poly1305
├── 非对称加密与密钥交换：RSA-OAEP、ECDH、X25519
├── 数字签名：RSA-PSS、Ed25519、ECDSA
└── 哈希与消息认证码：SHA-256、HMAC-SHA-256
                 ↓ 被组合使用
场景与协议
├── 接口通信：HTTPS + 调用方认证 + 可选的请求签名或应用层加密
├── License：Ed25519 签发与验签
├── SSH：主机认证 + 用户认证 + 密钥交换 + 会话加密
└── HTTPS/TLS：证书认证 + 密钥交换 + 会话加密
```

## 第一部分：基础算法

### 1. 先按安全能力选择

| 编码需求 | 能力类型 | 推荐算法或机制 | 密钥关系 |
| --- | --- | --- | --- |
| 加密大量正文、文件或数据库字段 | 对称加密 | AES-GCM；特定平台可用 ChaCha20-Poly1305 | 加密方和解密方持有同一密钥 |
| 接收方公开加密入口，只有自己能解密 | 非对称加密 | RSA-OAEP 加密临时 AES 密钥 | 接收方持私钥，发送方持接收方公钥 |
| 双方通过公开通信协商会话密钥 | 密钥交换 | ECDH 或 X25519 + HKDF | 双方各持自己的私钥，交换公钥 |
| 证明内容由指定主体签发且未被修改 | 数字签名 | Ed25519；需 RSA 兼容时使用 RSA-PSS | 签名方持私钥，验证方持签名方公钥 |
| 计算不可逆的数据摘要 | 哈希 | SHA-256 或 SHA-512 | 没有密钥 |
| 共享秘密的双方校验消息来源和完整性 | 消息认证码 | HMAC-SHA-256 | 双方共享同一个秘密密钥 |
| 安全存储用户密码 | 密码哈希 | Argon2id；按平台能力选择 scrypt、bcrypt 或 PBKDF2 | 存储盐和参数，不保存可解密的密码 |

“加解密”是常用统称，但哈希、消息认证码、数字签名和密钥交换都不是加密。Base64 只是编码，也不提供任何保密性。

- [数字签名](基础算法/数字签名.md)：RSA-PSS、Ed25519、ECDSA，以及签名方和验证方的密钥归属。

### 3. 基础密钥原则

| 类型 | 谁生成密钥 | 谁持有秘密 | 谁持有公开信息 |
| --- | --- | --- | --- |
| 对称加密 | 由受控密钥系统或负责加密的一方生成 | 所有获准加解密的参与方 | 无公钥 |
| 非对称加密 | 最终负责解密的一方生成 | 解密方持私钥 | 加密方持解密方公钥 |
| 数字签名 | 最终负责签名的一方生成 | 签名方持私钥 | 验证方持签名方公钥 |
| HMAC | 一方生成后通过安全渠道共享，或由统一密钥系统分发 | 通信双方都持有同一密钥 | 无公钥 |
| 密钥交换 | 每个参与方分别生成自己的密钥对 | 各方只持有自己的私钥 | 交换各自公钥 |

同一种算法用于不同场景时也必须使用不同密钥。例如，Ed25519 License 私钥、Ed25519 SSH 用户私钥和 SSH 主机私钥必须完全独立。

## 第二部分：场景与协议

### 1. 场景与协议如何使用算法

| 场景或协议 | 它是什么 | 内部组合的能力 | 业务代码主要决定什么 |
| --- | --- | --- | --- |
| 接口通信 | 应用场景 | HTTPS、Token/mTLS、可选请求签名和应用层加密 | 调用方身份、权限、防重放及是否需要端到端报文保护 |
| License | 业务授权场景 | 通常使用 Ed25519 数字签名 | 授权字段、签发、验签、有效期、绑定和轮换策略 |
| SSH | 安全远程登录与传输协议 | 主机/用户签名、密钥交换、对称会话加密 | 用户与主机信任、密钥分发和算法配置 |
| HTTPS/TLS | HTTP 的安全传输协议 | 证书、数字签名、密钥交换、对称会话加密 | 证书来源、服务端/客户端认证和 TLS 终止边界 |

协议通常已经规定如何组合算法。业务开发应使用成熟协议和密码库，不应自己照着密码学原理重新实现 SSH 或 TLS。

### 2. 场景与协议专题

- [接口通信安全](场景与协议/接口通信安全.md)：HTTPS、调用方认证、RSA/Ed25519 请求签名和应用层混合加密如何组合。
- [License 授权场景](场景与协议/License授权场景.md)：谁生成 Ed25519 密钥，谁签发，客户程序如何验签。
- [SSH 协议中的密钥与加密](场景与协议/SSH协议.md)：用户密钥、主机密钥和会话密钥分别负责什么。
- [HTTPS/TLS 协议中的证书与加密](场景与协议/HTTPS-TLS协议.md)：服务器证书、CA、私钥、密钥交换和流量加密的关系。

### 3. 最常见的组合结论

- 普通 API：HTTPS/TLS + 每个调用方独立的短期 Token 或客户端凭证。
- 高安全内部 API：HTTPS/TLS + mTLS，并在应用层继续执行账号和权限校验。
- 报文需脱离连接独立验真：HTTPS/TLS + RSA-PSS、Ed25519 或约定的请求签名机制。
- TLS 终止后中间系统仍不能看到正文：HTTPS/TLS + AES-GCM/RSA-OAEP 等标准应用层加密信封。
- License：厂商 Ed25519 私钥签发，客户程序内置厂商公钥验签。
- SSH：协议自己协商会话加密；运维侧重点是分别管理用户密钥和服务器主机密钥。

无论采用哪种协议，私钥都不应通过聊天、邮件、普通共享目录或源码仓库传输；生产环境优先使用 KMS、HSM、TPM、Vault 或操作系统密钥库。
