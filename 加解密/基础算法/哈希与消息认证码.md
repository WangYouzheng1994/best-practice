# 哈希与消息认证码

> 作者：王有政
>
> 编码：UTF-8

哈希、HMAC、密码哈希和 Base64 经常被误称为“加密”，但它们的用途不同，也都不能通过“解密”恢复原文。

## 一、能力对比

| 类型 | 是否使用密钥 | 能否恢复原文 | 主要用途 | 推荐方案 |
| --- | --- | --- | --- | --- |
| 通用哈希 | 否 | 否 | 文件摘要、内容标识、签名前摘要 | SHA-256、SHA-512 |
| HMAC | 是，双方共享秘密 | 否 | 两个共享密钥方之间的消息认证 | HMAC-SHA-256 |
| 密码哈希 | 使用随机盐和成本参数 | 否 | 存储用户密码验证值 | Argon2id，或 scrypt、bcrypt、PBKDF2 |
| Base64 | 否 | 可以直接解码 | 把二进制表示成文本 | 只作编码，不作安全保护 |

## 二、通用哈希

哈希把任意长度数据映射为固定长度摘要：

```text
原始文件或正文 → SHA-256 → 固定长度摘要
```

改变一个字节通常会得到完全不同的摘要。但单独发送“文件 + SHA-256”不能证明来源，因为攻击者可以同时替换文件和摘要。需要来源认证时，应使用数字签名或 HMAC。

新系统使用 SHA-256 或 SHA-512。MD5 和 SHA-1 存在碰撞安全问题，不能用于新设计中的签名、证书或对抗性完整性校验。

## 三、HMAC

HMAC 使用双方共享的秘密密钥计算消息认证码：

```text
发送方：HMAC(共享密钥, 消息) → tag
接收方：使用相同共享密钥重新计算并安全比较 tag
```

HMAC 能证明消息由“某个共享密钥持有者”生成并且未被修改，但通信双方都能生成合法 HMAC，因此不能向第三方证明具体是哪一方生成。参与方越多，共享密钥的责任边界越差。

HMAC 密钥由一方使用安全随机数生成后通过安全渠道共享，或由统一密钥系统分发。每个客户和用途使用独立密钥，并使用常量时间比较验证 tag。

## 四、密码存储

用户密码不能使用 AES 加密后保存，也不能只计算一次 SHA-256。应使用专用密码哈希算法和每个密码独立的随机盐：

```text
用户密码 + 随机盐 + 成本参数
        ↓
Argon2id 等密码哈希
        ↓
保存算法、参数、盐和结果
```

验证登录时使用相同参数重新计算并比较。盐可以公开，作用是防止相同密码产生相同结果和抵抗预计算表；可选的 pepper 属于服务端秘密，必须与数据库分开保存。

## 五、Base64 不是加密

Base64 只是文本编码，任何拿到内容的人都能无密钥解码。它适合在 JSON、环境变量或文本协议中表示密钥、签名和密文，但不能保护这些内容。

```text
Base64：可逆编码，不需要密钥
哈希：不可逆摘要，不需要密钥
HMAC：不可逆认证码，需要共享密钥
加密：使用密钥把明文转换为可恢复的密文
```

## 六、常见场景

| 场景 | 正确做法 |
| --- | --- |
| 校验下载文件是否与发布方一致 | 发布方对文件或摘要做数字签名；仅哈希不足以认证发布方 |
| 两个内部系统对请求做轻量认证 | HTTPS + 每个调用方独立的 HMAC 密钥，并增加时间戳和 Nonce |
| 生成硬件指纹 | 对规范化硬件标识做 SHA-256；同时明确稳定性和隐私边界 |
| 存储用户密码 | Argon2id 等密码哈希，不可逆加密或普通 SHA-256 |
| 在 JSON 中携带签名字节 | Base64 编码签名，但安全性来自签名而非 Base64 |

## 七、禁止事项

1. 禁止把 Base64 称为加密。
2. 禁止用 MD5、SHA-1 或普通 SHA-256 存储用户密码。
3. 禁止把公开哈希值当作身份认证凭证。
4. 禁止多个客户共用一个 HMAC 密钥。
5. 禁止在普通字符串比较函数可能泄漏时序信息的环境中直接比较 HMAC。
