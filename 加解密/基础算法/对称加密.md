# 对称加密

> 作者：王有政
>
> 编码：UTF-8

对称加密使用同一个秘密密钥完成加密和解密，适合处理大量数据。HTTPS、SSH 和应用层混合加密最终都依靠对称算法加密实际正文。

## 一、适用场景

- 加密数据库敏感字段、文件、备份或消息正文。
- 加密接口中的大段业务数据。
- 加密 SSH、TLS 等协议协商出来的会话流量。
- 作为信封加密的数据密钥，由 KMS 或非对称算法保护该数据密钥。

对称加密不适合直接解决陌生双方的密钥分发问题，因为加密方和解密方必须预先安全获得同一个密钥。

## 二、算法选择

| 方案 | 定位 | 结论 |
| --- | --- | --- |
| AES-GCM | 认证加密，同时提供保密性和完整性 | 默认推荐 |
| ChaCha20-Poly1305 | 认证加密，在无 AES 硬件加速的平台上表现良好 | 移动端或特定平台可选 |
| AES-CBC | 只提供加密，还需单独正确组合 MAC 和填充处理 | 新系统不推荐 |
| AES-ECB | 相同明文块产生相同密文块，会泄漏数据结构 | 禁止使用 |

优先使用 AEAD，即“带关联数据的认证加密”。AES-GCM 和 ChaCha20-Poly1305 都会同时输出密文和认证标签，解密时标签不匹配必须整体失败。

## 三、谁生成和保存密钥

1. 密钥由密码学安全随机数生成器、KMS 或 HSM 生成，不能由人编写一个可读字符串充当密钥。
2. 所有需要解密的参与方都必须获得该密钥，因此参与方越多，泄漏面越大。
3. 应用只通过密钥标识引用生产密钥，优先让 KMS 或密钥代理执行解密操作。
4. 每个环境、租户和用途使用独立密钥，不与 HTTPS、SSH、License 或 HMAC 密钥复用。

## 四、AES-GCM 如何使用

一次加密至少涉及：

| 数据 | 作用 | 是否保密 |
| --- | --- | --- |
| `keyId` | 指明解密端使用哪个密钥版本 | 否 |
| `nonce` | 保证同一密钥下每次加密唯一 | 否 |
| `ciphertext` | 加密后的正文 | 是 |
| `tag` | 验证密文和关联数据未被修改 | 否 |
| `aad` | 不加密但必须防篡改的上下文 | 否 |

```text
加密方取得数据密钥
        ↓
为本次加密生成唯一 Nonce
        ↓
确定 AAD，例如 version、alg、keyId、租户和业务类型
        ↓
AES-GCM 输出 ciphertext 和 tag
        ↓
解密方使用相同 key、nonce、AAD 验证并解密
```

同一 AES-GCM 密钥下绝不能重复使用 Nonce。Nonce 重复会严重破坏保密性和完整性。不要把 Nonce 当成私密数据，但必须保证其生成策略正确。

## 五、信封加密

生产系统不应使用一把长期主密钥直接加密所有正文。推荐使用信封加密：

```text
每批或每条数据生成随机数据密钥 DEK
        ↓
DEK 使用 AES-GCM 加密业务正文
        ↓
KMS 主密钥或接收方 RSA 公钥加密 DEK
        ↓
保存 encryptedDEK、nonce、ciphertext、tag 和受认证元数据
```

主密钥轮换时通常只需重新保护 DEK，不必立即重新加密全部业务正文。优先使用 JWE、COSE 或云 KMS 提供的标准信封格式，不自行发明字段和编码规则。

## 六、禁止事项

1. 禁止把密码直接补零、截断或做一次 SHA-256 后当作 AES 密钥；密码派生应使用专用 KDF。
2. 禁止在同一密钥下重复使用 GCM Nonce。
3. 禁止只保存密文而丢弃认证标签、Nonce、算法版本或 `keyId`。
4. 禁止在认证标签验证失败后返回部分明文。
5. 禁止把密钥硬编码到源码、前端包、容器公共镜像层或日志中。
