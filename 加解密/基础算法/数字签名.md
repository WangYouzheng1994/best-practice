# 数字签名

> 作者：王有政
>
> 编码：UTF-8

数字签名用于证明数据由对应私钥持有者签发，并检测签名覆盖内容是否被修改。数字签名不隐藏正文，也不能代替传输加密。

## 一、谁生成和持有密钥

需要对外证明自己身份的一方生成签名密钥对：

```text
签名方
  私钥：只由签名方保存，用于生成签名
  公钥：通过可信渠道发给验证方

验证方
  保存签名方公钥及其身份、用途、keyId 的可信映射
```

License 场景由软件厂商生成并持有私钥；接口请求签名由每个下游分别生成并持有自己的私钥。上游代替下游生成并传输私钥会扩大泄漏风险，不作为默认方案。

## 二、签名与验签流程

```text
签名方确定必须保护的全部字段
        ↓
按固定规则生成待签名字节
        ↓
使用私钥生成签名
        ↓
发送原始数据、keyId、算法标识和签名
        ↓
验证方从本地信任集合查找公钥
        ↓
按相同规则重建待签名字节并验签
        ↓
验签通过后再执行时间、权限、有效期等业务校验
```

验签前的 `keyId` 只能用于本地白名单查找候选公钥，不能指示程序从不可信地址下载公钥，也不能允许调用方任意选择弱算法。

## 三、算法选择

| 算法 | 特点 | 适用场景 |
| --- | --- | --- |
| Ed25519 | 密钥和签名短、速度快、参数简单，只能签名 | 新设计的 License、令牌、文件或应用层报文签名，推荐 |
| RSA-PSS | RSA 生态成熟、跨系统兼容广，但密钥和签名较大 | 已有 RSA 基础设施、兼容性或合规要求的接口签名 |
| ECDSA | 证书和硬件生态广，但实现必须正确处理随机数和编码 | TLS 证书、硬件设备或既有 PKI 体系 |

接口请求签名不天然等于 RSA。新系统可根据兼容性选择 Ed25519，RSA 体系使用 RSA-PSS；通信双方能够安全共享秘密且不需要第三方独立验真时，也可以评估 HMAC。

## 四、签名原文必须确定

JSON 字段顺序、空格、数字格式和换行变化都会改变字节。双方必须固定：

- UTF-8 编码。
- 字段集合和排列顺序。
- 空值、布尔值、数字和时间格式。
- 路径、查询参数与请求头的规范化规则。
- 签名覆盖的是原文、摘要、密文还是完整信封。
- 协议版本、算法标识和 `keyId` 是否进入受保护范围。

能使用 JWS、COSE Sign1 等标准封装时优先使用标准，不自行设计字符串拼接协议。

## 五、签名不自动解决的问题

| 问题 | 仍需增加的措施 |
| --- | --- |
| 正文保密 | HTTPS/TLS 或应用层对称加密 |
| 请求重放 | 时间戳、Nonce、短有效期和服务端去重 |
| 调用权限 | 把公钥身份映射到账号、角色和具体权限 |
| 私钥被盗 | 密钥撤销、轮换、审计和安全存储 |
| 客户端程序被篡改 | 代码签名、完整性保护、安全启动或服务端校验等独立措施 |

数字签名能证明“对应私钥生成了签名”，前提是私钥确实只属于声明的签名方，且验证方通过可信渠道获得正确公钥。

## 六、密钥轮换

1. 生成新密钥对并分配新的 `keyId`。
2. 验证方先加入新公钥，同时保留仍需验证历史数据的旧公钥。
3. 签名方切换到新私钥。
4. 旧签名全部过期或完成迁移后，再撤销旧公钥。

私钥泄漏时不能只更换证书名或 `keyId`，必须生成全新密钥对、停止信任旧公钥，并评估泄漏期间签发的数据。

## 七、禁止事项

1. 禁止把签名描述成“私钥加密、公钥解密”。
2. 禁止只签部分授权字段或请求字段，给未签名字段留下篡改空间。
3. 禁止所有客户共用一把请求签名私钥。
4. 禁止使用 SHA-1 或新增 RSA PKCS#1 v1.5 签名方案。
5. 禁止复用 License、接口、SSH 和 HTTPS 私钥。
