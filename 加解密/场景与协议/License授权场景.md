# License 授权场景

> 作者：王有政
>
> 编码：UTF-8

License 是业务应用场景，不是密码算法。它的核心目标通常不是隐藏内容，而是让客户程序确认：License 确实由软件厂商签发，并且客户、产品、功能、有效期和硬件绑定等内容没有被修改。

本规范选择 Ed25519 实现 License 数字签名。Ed25519 的算法定位和其他签名算法对比参见[数字签名](../基础算法/数字签名.md)。

## 一、密钥由谁生成

1. 软件厂商或 License 签发方在受控环境中生成 Ed25519 密钥对。
2. 私钥只供 License 签发端使用，不进入客户环境。
3. 公钥内置到客户软件或可信运行时中，只用于验签。
4. 每个密钥版本分配唯一 `keyId`，客户端可同时信任处于轮换期的新旧公钥。

```text
厂商受控环境
  Ed25519 私钥：生成 License 签名
  Ed25519 公钥：随软件发布

客户运行环境
  只有 Ed25519 公钥：验证 License
```

客户拿到公钥后只能验证签名，不能生成新的合法 License。公钥被读取不是安全事件；私钥泄漏才会导致攻击者能够伪造 License。

## 二、License 应包含什么

License 建议明确分为受保护头、载荷和签名。受保护头至少包含：

| 字段 | 作用 |
| --- | --- |
| `version` | License 协议版本 |
| `alg` | 固定允许的签名算法，本规范为 Ed25519 |
| `keyId` | 指明从客户端本地信任集合选择哪个厂商公钥 |

License 载荷使用固定结构和确定性序列化规则，至少明确：

| 字段 | 作用 |
| --- | --- |
| `licenseId` | License 唯一编号，便于审计和吊销 |
| `customerId` | 被授权客户 |
| `productCode` | 被授权产品 |
| `features` | 可使用的功能范围 |
| `issuedAt` | 签发时间 |
| `notBefore` | 最早生效时间 |
| `expiresAt` | 到期时间；永久授权也应使用明确规则表达 |
| `deploymentId` | 服务集群或部署实例的稳定标识 |
| `hardwareFingerprint` | 需要硬件绑定时使用的规范化指纹 |

是否绑定 MAC、主板序列号或其他硬件信息属于业务策略，不属于 Ed25519 算法本身。硬件采集规则必须稳定，并考虑网卡更换、虚拟机迁移、容器环境和集群扩缩容。

## 三、签发流程

```text
签发端接收已审核的授权申请
        ↓
按固定字段和顺序生成受保护头与 License 载荷
        ↓
分别使用确定性格式序列化为 UTF-8 字节
        ↓
对“受保护头 + 明确分隔符 + 载荷”构造唯一签名输入
        ↓
使用厂商 Ed25519 私钥对完整签名输入签名
        ↓
输出 protectedHeader、payload、signature 组成的 License
        ↓
记录 licenseId、客户、有效期、keyId 和签发审计信息
```

签名必须覆盖 `version`、`alg`、`keyId` 和所有影响授权结果的载荷字段。不能把客户、有效期、功能列表或硬件指纹放在签名范围之外。

## 四、客户程序验签流程

```text
读取 License
        ↓
按严格长度和格式限制解析未受信的 protectedHeader、payload 和 signature
        ↓
拒绝不支持的 version、alg，并根据 keyId 从本地内置信任集合查找候选公钥
        ↓
重建“受保护头 + 明确分隔符 + 载荷”并验证 signature
        ↓
验签通过后再解析并检查客户、产品、有效期、功能和硬件绑定
        ↓
全部通过才允许受控功能运行
```

处理顺序应为“受限解析、选择本地候选公钥、验签、再信任字段”。验签前的 `version`、`alg` 和 `keyId` 只能用于拒绝非法输入和本地白名单查找，不能据此下载公钥、启用任意算法或决定授权结果。

验签成功只证明 License 来源可信且内容未被篡改，仍需执行以下业务校验：

- License 是否已经生效或已经过期。
- 产品代码和软件版本是否匹配。
- 客户、部署实例或集群标识是否匹配。
- 硬件指纹是否符合既定容差策略。
- License 是否被吊销。
- 功能和容量是否在授权范围内。

## 五、License 为什么通常不加密

License 中的客户、功能、有效期等内容通常不属于必须保密的信息。加密 License 还会引入客户侧解密密钥，而客户程序中的解密密钥最终可以被提取，不能作为可靠的授权保护边界。

如果 License 确实包含敏感数据，应优先删除或最小化这些字段。确实需要保密时，应该把“签名防伪”和“数据加密”设计成两个独立层次，不能错误地认为 Ed25519 能够加密。

## 六、威胁边界

Ed25519 可以阻止未被篡改的客户程序接受伪造或被修改的 License，但不能单独阻止控制客户机器的攻击者：

- 修改程序以跳过验签或业务校验。
- 替换程序内置公钥并使用攻击者私钥重新签名。
- Hook 验签结果或修改内存中的授权状态。
- 回拨系统时间以绕过离线有效期检查。
- 伪造软件能读取到的 MAC、主板号或其他硬件标识。

因此，License 签名是授权体系的重要一层，不是绝对的客户端防破解方案。可按风险增加代码签名、完整性检查、可信时间、在线激活或周期校验，但不应承诺在攻击者完全控制的机器上实现不可绕过。

## 七、私钥保存方案

生产环境按安全等级优先选择：

1. HSM、KMS 或受控签名服务：私钥不可导出，签发操作有身份认证和审计，推荐用于正式生产。
2. 离线签发机：私钥加密保存，仅在授权审批后由少数人员操作，适合签发频率较低的场景。
3. 服务端加密私钥文件：只适合风险可控的内部环境；必须限制文件权限、分离解密口令并记录签发审计。

开发测试必须使用独立密钥，不能复制生产私钥。生产私钥也不能写入源码、配置中心明文、普通数据库字段或应用日志。

## 八、密钥轮换

1. 生成新的 Ed25519 密钥对并分配新的 `keyId`。
2. 先发布同时信任新旧公钥的客户端版本。
3. 确认主要客户已经升级后，签发端切换到新私钥。
4. 旧 License 仍在有效期内时保留旧公钥。
5. 旧 License 全部失效或完成换发后，再从后续客户端版本移除旧公钥。

如果私钥泄漏，应立即停止使用该 `keyId`，发布不再信任对应公钥的客户端版本，并重新签发受影响的 License。由于离线客户端无法实时获取吊销列表，离线 License 必须提前设计有效期和升级策略。

## 九、与 RSA、SSH、HTTPS 的边界

| 技术 | 在此体系中的职责 |
| --- | --- |
| Ed25519 License 签名 | 证明 License 由厂商签发且未被修改 |
| HTTPS/TLS | 保护在线申请、签发和下载 License 的传输链路 |
| SSH 密钥 | 认证运维人员或自动化程序能否登录签发服务器 |
| RSA 接口签名 | 存在兼容性要求时认证调用 License 服务的下游请求 |

这些用途必须使用不同密钥。即使 SSH 也选择 Ed25519，SSH 用户密钥、SSH 主机密钥和 License 签发密钥仍是三套完全独立的密钥。

## 十、禁止事项

1. 禁止把 License 签发私钥打包进客户程序。
2. 禁止允许客户程序下载或替换“可信公钥”而不校验其来源。
3. 禁止只解析 License 字段而不验证签名。
4. 禁止在验签前信任 `version`、`alg`、`keyId` 或任何载荷字段；它们只能用于受限解析和本地白名单查找。
5. 禁止依赖代码混淆保护签发私钥。
6. 禁止复用 SSH、HTTPS 或接口签名密钥签发 License。
7. 禁止把 Ed25519 当作公钥加密算法使用。
