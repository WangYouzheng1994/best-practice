# 接口通信安全

> 作者：王有政
>
> 编码：UTF-8

接口通信安全不是在 HTTPS 和 RSA 之间二选一。HTTPS/TLS 是所有生产接口的传输安全基线；Token、mTLS 或请求签名负责识别调用方；只有存在端到端报文保密要求时，才额外使用应用层混合加密。

本文重点说明接口场景如何组合协议和密码算法。基础概念参见[对称加密](../基础算法/对称加密.md)、[非对称加密与密钥交换](../基础算法/非对称加密与密钥交换.md)、[数字签名](../基础算法/数字签名.md)与[HTTPS/TLS 协议](HTTPS-TLS协议.md)。

## 一、先确定保护层级

| 层级 | 默认做法 | 什么时候增加其他机制 |
| --- | --- | --- |
| 传输保密、完整性和服务端身份 | 所有生产接口使用 HTTPS/TLS | TLS 在网关终止后仍需保护正文时，增加应用层加密 |
| 调用方身份和业务权限 | 每个下游使用独立客户端凭证换取短期 Token | 需要机器级强身份时使用 mTLS |
| 报文脱离连接后仍可独立验真 | 默认依赖 TLS 和调用方认证 | 跨中间节点、留存验真或明确防抵赖边界时增加请求签名 |
| 应用层正文保密 | 默认不重复加密 | 中间系统不得看到正文时使用标准混合加密信封 |

“公钥加密、私钥解密”描述的是 RSA 加密。“私钥签名、公钥验签”描述的是数字签名。不要把签名描述为“私钥加密、公钥解密”，二者的安全目的和标准格式不同。

## 二、场景一：应用层正文保密

### 推荐结论

普通接口首先使用 HTTPS/TLS。只有数据经过网关、消息队列、日志系统或 TLS 终止节点后仍必须保持密文时，才增加应用层混合加密。

RSA 不适合直接加密整个请求：可加密数据长度受密钥长度和填充方式限制，性能也远低于对称加密。正确方式是使用 AES-GCM 加密正文，再使用 RSA-OAEP 加密一次性的 AES 密钥。

### 密钥由谁生成

1. 上游生成 RSA 加密密钥对。
2. 上游独占保存 RSA 私钥。
3. 上游通过可信渠道把 RSA 公钥交给下游。
4. 公钥分配 `keyId`，便于上游以后轮换密钥。

### 请求流程

```text
下游生成一次性 AES-256 密钥和随机 Nonce
        ↓
使用 AES-GCM 加密请求正文，得到 ciphertext 和 authentication tag
        ↓
使用上游 RSA 公钥和 RSA-OAEP 加密 AES 密钥
        ↓
把 version、alg、keyId、encryptedKey、nonce 等元数据作为 AAD 或签名保护范围
        ↓
发送 protectedMetadata、encryptedKey、nonce、ciphertext、tag
        ↓
上游根据 keyId 找到 RSA 私钥，解出 AES 密钥
        ↓
上游使用 AES-GCM 解密并验证正文完整性
```

每个请求必须重新生成 AES 密钥或至少保证同一 AES 密钥下的 Nonce 永不重复。`version`、`alg`、`keyId`、`encryptedKey` 和 `nonce` 等未加密元数据也必须通过 AEAD 的 AAD 或数字签名防篡改。优先使用 JWE、COSE 或成熟 KMS 信封格式，不自行设计加密协议。

### 这套机制不证明下游身份

任何得到上游公钥的人都能构造密文。因此，应用层加密仍需配合 Token、mTLS 或请求签名识别调用方。

## 三、场景二：识别下游并防止请求被篡改

### 密钥由谁生成

1. 每个下游在自己的受控环境生成独立的签名密钥对，算法由接口协议统一确定。
2. 下游保存自己的私钥，不把私钥交给上游。
3. 下游把公钥登记到上游。
4. 上游保存 `clientId -> keyId -> publicKey` 的可信映射。

由下游自己生成私钥是推荐方式。若上游代为生成再把私钥交给下游，会增加私钥传输、留存副本和责任边界不清等风险。

### 签名内容

不能只签请求正文。建议对以下字段形成唯一、稳定的规范化字符串后再签名：

```text
协议版本
clientId
keyId
HTTP 方法
请求路径
规范化查询参数
请求正文哈希
时间戳
Nonce
```

请求头、字段排序、字符编码、空值和换行符规则必须固定，否则双方对同一请求可能得到不同签名原文。正文统一使用 UTF-8；正文摘要建议使用 SHA-256。

### 请求流程

```text
下游构造请求和规范化签名原文
        ↓
下游使用自己的签名私钥生成签名
        ↓
携带 clientId、keyId、timestamp、nonce、signature 调用上游 HTTPS 接口
        ↓
上游根据 clientId 和 keyId 查找该下游公钥
        ↓
上游重建签名原文并验签
        ↓
上游检查时间窗口和 nonce 是否已使用
        ↓
验签及防重放检查全部通过后处理业务
```

验签成功只能证明请求由对应私钥持有者签发且签名内容未被修改。上游还必须检查权限、时间戳和 Nonce。

请求签名不天然等于 RSA。已有 RSA 基础设施或兼容性要求时使用 RSA-PSS；新系统在各语言和密码库都兼容时可以选择 Ed25519；封闭系统能够安全分发共享密钥且不要求第三方独立验真时，可以评估 HMAC。算法必须由协议固定，不能由调用方任意降级选择。

## 四、场景三：既加密又签名

同时需要应用层保密和下游身份认证时，需要两套不同的密钥关系：

```text
上游 RSA 加密密钥对
  私钥：上游保存，用于解密临时 AES 密钥
  公钥：下游保存，用于加密临时 AES 密钥

每个下游的独立签名密钥对（RSA-PSS 或协议确定的其他算法）
  私钥：下游保存，用于请求签名
  公钥：上游登记，用于识别下游并验签
```

协议必须固定“先签名后加密”还是“先加密后签名”，并明确签名覆盖明文、密文还是完整信封，不能由调用方自由选择。能使用 JWE、JWS 或 COSE 等标准组合时优先使用标准。

## 五、RSA 方案与通用参数基线

| 项目 | 推荐值 |
| --- | --- |
| RSA 密钥长度 | 至少 3072 位；如受既有兼容性约束，最低不得低于 2048 位 |
| RSA 加密填充 | OAEP，摘要使用 SHA-256 |
| RSA 签名填充 | PSS，摘要使用 SHA-256 |
| 正文对称加密 | AES-256-GCM；受平台约束时可使用 AES-128-GCM |
| 正文摘要 | SHA-256 |
| 时间戳有效窗口 | 根据系统时钟可靠性设定，常见为 5 分钟以内 |
| Nonce | 密码学安全随机值，并在有效窗口内做服务端去重 |
| 字符编码 | UTF-8 |

新系统不应使用 RSA PKCS#1 v1.5 加密，也不应新增 SHA-1 签名。算法名称、协议版本和 `keyId` 应显式进入报文，不能依赖双方默认值。

## 六、什么时候不增加 RSA 方案

- 只需要传输加密：直接使用 HTTPS/TLS。
- 只需要登录态或服务授权：使用短期 Token、OAuth 2.0 客户端凭证或 mTLS。
- 双方都在同一受控系统且可以安全共享密钥：HMAC 可能更简单，但共享密钥会扩大泄漏影响范围。
- 新设计只需要高性能签名且不存在 RSA 兼容性要求：可以评估 Ed25519，但必须先确认语言、密码库、证书体系和合规要求。

## 七、禁止事项

1. 禁止所有下游共用一对签名密钥。
2. 禁止把上游解密私钥或下游签名私钥放入前端代码、镜像公共层或源码仓库。
3. 禁止只验签、不检查时间戳和 Nonce。
4. 禁止直接用 RSA 加密任意长度的 JSON 或文件。
5. 禁止用 Base64 代替加密；Base64 只是编码。
6. 禁止关闭 HTTPS 证书校验来“解决”联调问题。
7. 禁止同一 RSA 密钥同时承担接口解密、请求签名、HTTPS 证书和其他业务用途。
