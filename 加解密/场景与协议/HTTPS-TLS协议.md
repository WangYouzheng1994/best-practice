# HTTPS/TLS 协议中的证书与加密

> 作者：王有政
>
> 编码：UTF-8

HTTPS 是运行在 TLS 加密连接中的 HTTP，不是单一的加密算法。TLS 会组合证书、[数字签名](../基础算法/数字签名.md)、[密钥交换](../基础算法/非对称加密与密钥交换.md)和[对称加密](../基础算法/对称加密.md)，负责确认服务端身份、协商会话密钥，并对请求和响应提供保密性与完整性。

## 一、HTTPS 中有哪些密钥和证书

| 对象 | 谁产生 | 保存位置 | 用途 |
| --- | --- | --- | --- |
| 服务器私钥 | 服务端、ACME 客户端或受控密钥系统生成 | HTTPS 服务端或密钥系统 | 证明服务器持有证书对应私钥 |
| 服务器证书 | CA 根据申请签发 | 服务端配置，并在握手时发给客户端 | 绑定域名、组织身份和服务器公钥 |
| CA 根证书 | 公共 CA、企业内部 CA | 客户端信任库 | 验证服务器证书链是否来自受信 CA |
| 临时密钥交换参数 | 客户端和服务端每次连接产生 | 本次连接内存 | 协商一次性的会话密钥 |
| TLS 会话密钥 | 双方在握手中派生 | 本次连接内存 | 使用对称算法加密实际 HTTP 流量 |

证书不是私钥，也不是“加密后的公钥”。证书主要包含身份信息、公钥、有效期、用途、签发者以及 CA 的数字签名。

## 二、服务器证书如何产生

推荐流程如下：

```text
服务端或受控密钥系统生成服务器密钥对
        ↓
私钥留在服务端，使用公钥和域名等信息生成 CSR
        ↓
把 CSR 提交给公共 CA 或企业内部 CA
        ↓
CA 完成域名或组织校验并使用 CA 私钥签发证书
        ↓
服务端配置自己的私钥、服务器证书和中间证书链
```

CSR 包含公钥，不包含私钥。采用 ACME 自动签发时，上述步骤由客户端自动完成，但私钥仍应留在最终服务端或受控密钥系统中。

推荐由最终服务端、负载均衡器或其受控密钥设备生成私钥，再把 CSR 交给 CA。CA 只需要申请者公钥并使用 CA 自己的私钥签发证书，不应取得服务器私钥。集中代生成并下发服务器私钥只能作为有严格传输、销毁和审计控制的特殊流程。

### 三类证书来源

| 方案 | 适用场景 | 客户端信任方式 |
| --- | --- | --- |
| 公共 CA 证书 | 公网网站、开放 API | 操作系统和浏览器通常已经信任公共根 CA |
| 企业内部 CA 证书 | 内部服务、企业设备和服务网格 | 统一把企业根 CA 安装到受控客户端信任库 |
| 自签名证书 | 本地开发、临时实验或极少量点对点场景 | 必须通过可信渠道固定证书或公钥；不适合大规模生产分发 |

生产公网服务推荐公共 CA，企业内部大规模服务推荐内部 CA。自签名证书本身也能加密，但缺少可扩展的身份信任链，不能靠“关闭证书校验”解决信任问题。

## 三、客户端如何确认服务器身份

客户端收到服务器证书后，至少检查：

1. 证书链是否能连接到客户端信任的根 CA。
2. CA 签名是否有效。
3. 当前访问域名是否包含在证书的 SAN 中。
4. 证书是否处于有效期内。
5. 证书用途是否允许服务器身份认证。
6. 在适用环境中检查吊销状态或执行证书固定策略。

只有这些检查通过，客户端才能合理相信证书中的公钥属于目标域名。关闭主机名或证书链校验会使连接容易受到中间人攻击，即使界面上仍显示“流量已加密”。

## 四、HTTP 内容到底怎么变成密文

现代 TLS 不会用服务器 RSA 公钥直接加密所有 HTTP 内容。以 TLS 1.3 为例：

```text
客户端与服务端协商 TLS 版本和密码套件
        ↓
双方通过临时（EC）DHE 密钥交换计算共享秘密
        ↓
服务端用证书对应私钥签署握手数据，证明服务器身份
        ↓
客户端验证证书链、域名和握手签名
        ↓
双方派生本次连接的对称会话密钥
        ↓
使用 AES-GCM 或 ChaCha20-Poly1305 加密 HTTP 请求和响应
```

服务器证书中的公钥主要用于验证握手签名。实际业务流量由临时会话密钥进行高效对称加密。TLS 1.3 不再使用旧式 RSA 密钥交换，并能通过临时密钥交换提供前向保密。

## 五、HTTPS 能不能知道下游是谁

普通 HTTPS 默认只认证服务端：下游能确认上游服务身份，但上游不能仅凭 TLS 连接确定具体下游客户。

上游识别下游有三种常用方案：

| 方案 | 如何识别下游 | 适用场景 |
| --- | --- | --- |
| HTTPS + Token/客户端凭证（推荐默认） | 每个下游使用独立身份换取短期 Token | 大多数 API 和微服务调用 |
| 双向 TLS（mTLS） | 每个下游持有独立客户端证书，服务端验证证书链和身份 | 企业内部、高安全服务、服务网格 |
| HTTPS + 请求签名 | 下游使用 RSA-PSS、Ed25519 或约定机制签署规范化请求，上游验签 | 开放平台、请求留存验真、防重放要求明确的接口 |

三种方案可以组合，但没有明确需求时不应全部叠加。普通 API 通常使用 HTTPS + 独立客户端凭证即可。

## 六、mTLS 中谁生成密钥

mTLS 在普通 HTTPS 的服务端证书之外，再为每个客户端配置客户端证书：

```text
服务端
  持有服务器私钥和服务器证书
  信任签发客户端证书的 CA

每个下游客户端
  持有自己的客户端私钥和客户端证书
  信任签发服务器证书的 CA
```

客户端密钥对应在客户端本机、TPM、KMS 或企业 PKI 的受控流程中生成。客户端私钥不应在多个客户之间共享。企业 PKI 使用 CA 私钥签发客户端证书；CA 私钥只属于 CA，不会下发给客户端或服务端。

服务端验证客户端证书后，还应把证书中的稳定身份映射到应用账号和权限。证书有效不等于拥有所有业务权限。

## 七、证书更新与生产要求

1. 对证书到期时间进行监控，并使用 ACME 或企业证书平台自动续期。
2. 续期后确认服务已经加载新证书，不能只检查磁盘文件。
3. 私钥文件仅允许服务账号读取；优先使用 KMS、HSM、TPM 或平台密钥库。
4. TLS 终止在负载均衡、网关或 Ingress 时，必须明确终止点之后是否继续使用 TLS。
5. 内部 CA 根证书应通过设备管理或配置管理系统分发，不能让用户手工关闭证书校验。
6. 每个环境、域名和用途使用独立密钥；测试环境不得复制生产私钥。
7. 最低启用 TLS 1.2，优先 TLS 1.3；禁用 SSL、TLS 1.0、TLS 1.1 和弱密码套件。
8. 私钥泄漏后立即更换密钥对、重新签发证书并按 CA 机制吊销旧证书。

## 八、HTTPS 与应用层加密的边界

HTTPS 保护的是两个 TLS 终止点之间的 HTTP 路径、查询参数、请求头和正文。如果流量在网关解密后以明文进入后端，网关和后续链路能够看到内容。

TLS 不隐藏全部网络元数据。观察者通常仍能看到源和目标 IP、端口、流量大小与时序；DNS 查询和未启用相应保护时的 SNI 还可能泄漏目标域名。因此，HTTPS 的准确边界是保护 TLS 连接中的应用数据，不等于隐藏一次通信的存在及所有网络特征。

只有出现以下明确要求时，才考虑应用层加密：

- TLS 在中间网关终止，但网关不得读取敏感字段。
- 报文进入消息队列、数据库或日志后仍必须保持密文。
- 业务数据跨越多个不完全可信的中间系统，只有最终接收方可以解密。

应用层加密不能替代 HTTPS，因为 HTTPS 还保护请求路径、请求头、响应、握手完整性和传输链路。需要时应使用“HTTPS + 应用层混合加密”，而不是二选一。

## 九、常见误解

- “HTTPS 就是客户端拿服务器 RSA 公钥加密请求”：不准确。现代 TLS 使用证书认证和临时密钥交换，再用对称会话密钥加密流量。
- “证书可以公开，所以私钥也能一起发”：错误。证书需要发给客户端，私钥必须只留在持有者处。
- “自签名证书不能加密”：错误。它能加密，但客户端缺少自动可信的身份链。
- “安装证书后上游就知道具体下游是谁”：普通 HTTPS 只认证服务端；识别下游需 Token、mTLS 或请求签名。
- “证书过期只影响浏览器提示”：错误。严格客户端会直接拒绝连接。
- “内网不需要 HTTPS”：错误。内网同样存在窃听、伪装、错误路由和横向移动风险。
