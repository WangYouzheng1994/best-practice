# SSH 协议中的密钥与加密

> 作者：王有政
>
> 编码：UTF-8

SSH 是安全远程登录和传输协议，不是单一的加密算法。它会组合[数字签名](../基础算法/数字签名.md)、[非对称密钥交换](../基础算法/非对称加密与密钥交换.md)和[对称加密](../基础算法/对称加密.md)，同时解决客户端确认服务器身份、服务器确认登录用户身份，以及双方建立加密连接三件事。

## 一、三类密钥不能混淆

| 密钥 | 谁生成 | 私钥放在哪里 | 公钥放在哪里 | 用途 |
| --- | --- | --- | --- | --- |
| SSH 主机密钥 | SSH 服务器安装或初始化时生成 | 服务器 `/etc/ssh/` | 客户端 `known_hosts` 保存主机公钥记录 | 证明连接的是正确服务器 |
| SSH 用户密钥 | 用户、运维人员或自动化程序生成 | 用户终端、跳板机或安全设备 | 目标账号的 `authorized_keys` | 证明登录者持有对应私钥 |
| SSH 会话密钥 | 客户端与服务器在每次连接中协商 | 只存在于本次连接两端的内存 | 不长期分发 | 加密本次连接的实际流量 |

用户密钥决定“谁可以登录”，主机密钥决定“登录的是哪台服务器”，会话密钥决定“本次传输如何保密”。

## 二、用户密钥登录流程

### 密钥由谁生成

每位用户应在自己的可信终端生成独立密钥对。自动化程序则在对应执行环境或密钥系统中生成。推荐使用 Ed25519 用户密钥；只有兼容性或合规要求不支持时，再使用至少 3072 位的 RSA 密钥。

```text
用户终端
  私钥：~/.ssh/id_ed25519，仅用户持有
  公钥：~/.ssh/id_ed25519.pub，可登记到服务器

目标服务器
  ~/.ssh/authorized_keys：保存允许登录该账号的用户公钥
```

### 认证过程

```text
客户端声明希望使用某个用户公钥登录
        ↓
服务器确认该公钥存在于目标账号的 authorized_keys
        ↓
客户端使用对应私钥签署本次连接相关数据
        ↓
服务器使用已登记的公钥验签
        ↓
验签成功，证明客户端持有私钥
```

私钥不会在登录过程中发送给服务器。服务器保存公钥即可验证用户身份。

## 三、主机身份校验

SSH 服务首次启动时通常会生成主机密钥，私钥保存在服务器。客户端第一次连接时看到的主机指纹就是该主机公钥的摘要。

客户端必须通过可信渠道核对首次连接的指纹，例如从资产平台、云控制台、配置管理系统或管理员处获取。指纹是主机公钥的摘要，便于人工核对；`known_hosts` 实际保存的是主机名或地址与主机公钥的可信记录。以后主机密钥发生变化时，SSH 会告警，以防止客户端连接到冒充服务器的中间人。

以下情况会导致主机密钥变化：

- 服务器重装后重新生成主机密钥。
- IP 或域名被分配给另一台服务器。
- 负载均衡后的节点未统一规划主机身份。
- 攻击者正在实施中间人攻击。

出现告警时应先核实原因，不能直接删除 `known_hosts` 中的旧记录并继续连接。

## 四、连接内容如何加密

SSH 不会使用用户公钥或主机公钥直接加密整个终端流量。完成主机身份认证的同时，双方通过密钥交换算法协商一次性的共享会话密钥，再用对称算法加密传输内容。

```text
主机密钥签名：证明服务器身份
        +
密钥交换：为本次连接协商临时会话密钥
        +
对称加密：加密命令、输出、文件和隧道数据
        +
用户密钥签名：证明登录用户身份
```

采用现代临时密钥交换时，即使服务器的长期主机身份私钥以后泄漏，攻击者通常也不能仅凭已录制的网络流量恢复历史会话密钥，这就是前向保密的价值。用户认证私钥用于证明登录用户身份，本来就不参与会话密钥派生。

## 五、Ed25519 和 RSA 在 SSH 中的含义

SSH 可以使用 Ed25519 或 RSA 作为用户密钥、主机密钥的签名算法，但它们在 SSH 中主要用于身份认证，不是直接加密会话正文。

| 选择 | 适用情况 |
| --- | --- |
| Ed25519（推荐） | 现代 OpenSSH 环境；密钥短、性能好、参数选择简单 |
| RSA 3072 位或以上 | 老旧系统兼容、特定硬件或合规体系要求 RSA |
| ECDSA | 已有平台明确要求或硬件支持时使用 |

旧的 `ssh-rsa` 通常特指使用 SHA-1 的 RSA 签名方式，现代 OpenSSH 已默认禁用。RSA 密钥本身不等于必须使用 SHA-1；现代实现可以使用 `rsa-sha2-256` 或 `rsa-sha2-512`。不要为了兼容旧系统而在所有服务器上全局重新启用弱算法。

## 六、生产管理要求

1. 每位人员、每个自动化程序使用独立密钥，不共用私钥。
2. 用户私钥应设置口令；自动化密钥无法人工输入口令时，应由受控代理或密钥系统托管。
3. `authorized_keys` 可限制来源地址、允许命令、端口转发等权限，自动化账号应按最小权限配置。
4. 人员离职、设备丢失或私钥疑似泄漏时，立即从所有服务器移除对应公钥。
5. 禁止把私钥提交到 Git、发送到群聊或复制到多人共享目录。
6. 主机重装或替换时，通过可信渠道发布新的主机指纹。
7. 生产环境应保留 SSH 登录审计，并优先通过堡垒机或统一身份入口管理。
8. License 签发密钥、HTTPS 私钥和 SSH 私钥不得互相复用。

## 七、常见误解

- “把公钥给服务器，服务器用它加密返回内容”：错误。用户公钥主要用于验签，会话内容由协商出的对称密钥加密。
- “公钥泄漏后必须立即换密钥”：通常错误。公钥本来就可以分发，但必须确保公钥与身份的对应关系可信。
- “服务器保存了我的私钥”：正常公钥登录不需要服务器持有用户私钥。
- “首次连接直接输入 yes 就安全”：只有核对主机指纹后确认才安全。
- “SSH 使用 Ed25519，所以可以复用 License 的 Ed25519 密钥”：错误。算法相同不代表用途相同，必须使用独立密钥对。
